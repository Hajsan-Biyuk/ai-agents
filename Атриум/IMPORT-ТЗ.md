> Дата: 06.07.2026 · Агент: @pars · Статус: согласование

## 1. Задача

**MVP от заказчика:** автоматическая **загрузка новых** и **обновление существующих** товаров на сайте из файлов поставщиков (Excel/JSON), с возможностью подключения новых поставщиков без переписывания системы.

### 2.3. Важные факты (дополнительная проверка витрины и админки, 06.07.2026)

1. **Товары поставщиков уже есть на сайте** — 34 тыс. товаров каталога это результат прежних импортов тех же поставщиков: найдены живые карточки AltaCera (напр. «Artdeco Wood FT3ARE08 Керамогранит AltaCera 410×410», 1590 ₽), товары Delacora и RGW; бренды `alma-ceramica`, `altacera`, `azario` заведены в `/info/brands/`. → **Upsert по артикулу критичен**: импорт будет обновлять существующие карточки, а не только создавать.
2. **Маппинг категорий фактически готов**: колонки «Путь» в файлах «с обработкой» (`Каталог///Плитка и керамогранит///Плитка для ванной`) совпадают с реальным деревом сайта (`/catalog/plitka/dlya-vannoy/`) — файлы готовились под этот сайт. `categories.yaml` формализуется реверсом, согласование нужно только для новых категорий.
3. **Опт/розница — один сайт**: два шаблона (`aspro_max` + `aspro_max_opt_site`) на одном сайте = режим Aspro «опт+розница» с типами цен BASE/OPT. На витрине выводится розничная цена.

## 3. Архитектура: «канонический формат + профили поставщиков»

**Принцип: поставщик — это конфигурация, а не код.** Ядро системы знает только канонический JSON; всё специфичное для поставщика — в его профиле.

```
Excel/JSON поставщика ─→ [Профиль (YAML-маппинг)] ─→ Канонический JSON
                                                          │
                                              валидация + dry-run отчёт
                                                          ↓ (подтверждение)
                                    [PHP-приёмник на сайте] ─→ upsert в Bitrix
```

### 3.1. Канонический формат товара

```json
{
  "article": "351005073-11",
  "supplier": "rgw",
  "brand": "RGW",
  "name": "Душевая перегородка RGW WA-050",
  "price_retail": 35500,
  "price_opt": null,
  "unit": "Штука",
  "in_stock": true,
  "quantity": 3,
  "categories": ["Душевые перегородки", "Сборные"],
  "collection": "WA",
  "description": "...",
  "photos": ["https://...jpg"],
  "attributes": { "Толщина полотна, мм": "6", "Цвет профиля": "Хром" },
  "meta": { "source_file": "...", "parsed_at": "..." }
}
```

Ядро фиксировано; любые специфичные характеристики («Диаметр слива», «Количество чаш») — в `attributes` (EAV).

### 3.2. Профиль поставщика (`import/suppliers/{key}/`)

```
suppliers/
├── artkera/
│   ├── profile.yaml      ← синонимы колонок, ключ upsert, цены, дефолты
│   ├── categories.yaml   ← категории поставщика → разделы сайта
│   └── reader.py         ← только для нестандартных форматов
├── rgw/
├── santehcentr/
└── _template/            ← заготовка для нового поставщика
```

Пример `profile.yaml`:

```yaml
key: rgw
brand_default: RGW
enabled: true
channel: ftp              # ftp | upload | api
reader: flat_excel        # flat_excel | hier_excel | api_json
upsert_key: article
synonyms:
  article: ["Артикул", "Артикул "]
  name: ["Наименование", "Название", "Нименование", "Наименование товара"]
  price_retail: ["Цена, руб.", "Цена", "Цена (розница), руб.", "Цена, руб"]
ignore: ["Unnamed: *"]
photo_limit: 16
```

### 3.3. Словарь атрибутов (общий, `import/attributes.yaml`)

Защита фильтра сайта от дублей свойств («Цвет» / «Цвет профиля» / «Цвет изделия»):

```yaml
COLOR:
  site_property: COLOR_REF2
  synonyms: ["Цвет", "Цвет профиля", "Цвет изделия"]
```

Правила:
- атрибут найден в словаре → пишется в существующее свойство сайта;
- не найден → отчёт «неизвестные атрибуты», создание только после одобрения (карантин).

### 3.4. Маппинг категорий (`categories.yaml` в профиле)

Дерево разделов сайта — SSOT; категории поставщика привязываются таблицей соответствий, согласованной с заказчиком **один раз** при онбординге:

```yaml
"Каталог///Плитка и керамогранит///Плитка для ванной": "/catalog/plitka/dlya-vannoy/"
```

Неизвестная категория → товары в карантин + строка в отчёте. **Автосоздание разделов запрещено.**

### 3.5. Правила upsert (ключ — артикул / `CML2_ARTICLE`)

| Ситуация | Действие |
|----------|----------|
| Артикул в файле и на сайте | **Обновить**: цены BASE/OPT, наличие, поля из файла |
| Артикул только в файле | **Создать**: карточка целиком (раздел, бренд, фото, свойства) |
| Артикул только на сайте | **Не трогать** (никаких удалений/деактиваций без явного `purge`-флага) |
| Дубликат артикула в файле | **Error** в dry-run отчёте |
| Коллизия поставщиков (один артикул) | Внутренний ключ `supplier + article`; свойство `SUPPLIER` на товаре; приоритет — настройкой |

### 3.6. Конвейер обработки

```
received → parsed → normalized → validated → dry-run → confirmed → imported → verified
                                     ↓ (аномалии: пустые артикулы, скачок цен ±50%, неизвестные категории)
                                 quarantine
```

Dry-run обязателен. Автоподтверждение — per-supplier (доверенным каналам).

## 4. Структура на сервере

### 4.1. Папка обмена (вне public_html)

```
import/
├── inbox/{supplier}/      ← СЮДА загружаются файлы (SFTP / панель Beget / FTP от RGW)
├── processed/{supplier}/  ← обработанные, с датой
├── quarantine/            ← файлы с ошибками + отчёт
├── reports/               ← отчёты по каждому импорту (JSON)
└── data/normalized/       ← канонический JSON по датам (история/откат)
```

### 4.2. Компоненты на сайте

```
public_html/local/
├── php_interface/atrium_import/AtriumImporter.php  ← класс импортёра (по образцу SlonInstallCatalog)
└── tools/import/receive.php                        ← endpoint: токен + JSON порциями (100–200 шт.)
```

Функции импортёра: upsert по `CML2_ARTICLE`; бренд → поиск/создание в справочнике `BRAND`; цены → `BASE`/`OPT`; секции по таблице маппинга; свойства по словарю атрибутов (+карантин новых); фото по URL → `CFile` (фоном); режим `?dry=1`; авторизация: токен в заголовке + IP-allowlist.

## 5. Этапы реализации

### Этап 1 — MVP (ядро)

| № | Работа | Результат / проверка |
|---|--------|----------------------|
| 1.1 | Конвертер `parsing/` Арткеры → канонический JSON; профиль `suppliers/artkera/`; фикс бага H1 (`PHOTO_PATTERNS` без f-string) + контроль дубликатов артикулов | JSON валиден, 1457 SKU, цены = РРЦ |
| 1.2 | PHP-импортёр + endpoint на dev-сайте | dry-run порцией 5 товаров, сверка отчёта |
| 1.3 | Полный dry-run Арткеры → согласование категорий → импорт | 3–5 карточек на витрине: цена, фото, раздел, фильтр |
| 1.4 | Профили RGW и Santehcentr (нормализация через тот же механизм) | dry-run обоих поставщиков |

**MVP готов**: «положили файл в `inbox/` → запустили → новинки добавились, цены обновились». Запуск: вручную или cron.

### Этап 2 — автоматизация и UI

| № | Работа |
|---|--------|
| 2.1 | Поддомен `import.…` (FastAPI): форма загрузки, dry-run отчёт, кнопка «Подтвердить», реестр поставщиков, журнал |
| 2.2 | FTP-канал RGW: поставщик кладёт прайс → cron обрабатывает автоматически |
| 2.3 | API Santehcentr: cron ежедневно обновляет остатки/цены |
| 2.4 | Полный словарь атрибутов; выгрузка «неизвестных атрибутов» на согласование |

### Этап 3 — по мере необходимости

- Офферы (ИБ 64): свод размеров/цветов RGW в SKU одного товара (вопрос ТЗ).
- Уведомления об импортах (email/Telegram).
- Приоритеты и стратегии цен при пересечении поставщиков.

## 6. Онбординг нового поставщика (чек-лист)

1. Получить образец файла / доступ к API.
2. `suppliers/_template/` → `suppliers/{key}/`; создать `inbox/{key}/`.
3. Разобрать образец: колонки → ядро, характеристики → `attributes`.
4. Заполнить `profile.yaml` (синонимы, ключ, цены, дефолты).
5. Выгрузить уникальные категории → `categories.yaml` → **согласовать с заказчиком**.
6. Дополнить словарь атрибутов.
7. Dry-run на полном файле → показать 5–10 карточек-примеров.
8. Импорт на dev → проверка витрины → включить канал (при доверии — автоподтверждение).

Трудоёмкость типового онбординга: ~0,5–1 час (без программирования).

## 7. Безопасность

- Доступы — только в `*.env` (в `.gitignore`); не коммитить, не вставлять в чаты; после сдачи — сменить.
- Endpoint: токен + IP-allowlist; файлы обмена — вне DOCUMENT_ROOT.
- Лимит размера загрузки, проверка расширений (`.xls/.xlsx/.json`).
- Никаких массовых удалений: purge — только явным флагом по ТЗ.
- Бэкап БД перед первым большим импортом (напоминание в регламенте).

### 8.2. Закрыто проверкой / закрывается при реализации

| Вопрос | Статус |
|--------|--------|
| Категории поставщиков → дерево сайта | **Закрыт**: «Путь» в файлах совпадает с деревом сайта (§ 2.3.2); `categories.yaml` формализуется реверсом, согласование — только для новых категорий |

| RGW: отдельные товары или SKU-офферы? | **Закрывается на этапе 1.4**: проверить схему существующих товаров RGW на сайте и повторить её |
